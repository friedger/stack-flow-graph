# Stacks Transaction Visualizer

A web application for visualizing and analyzing Stacks blockchain transactions related to the SIP-031 endowment program. This tool provides interactive network graphs, transaction tables, and address balance tracking to help understand the flow of STX tokens through the network.

## About This Project

This site analyzes STX transfers indexed by [Secondlayer](https://secondlayer.tools). The analysis starts from the SIP-031 contract and the endowment address (currently `SM1Z6BP8PDKYKXTZXXSKXFEY6NQ7RAM7DAEAYR045`) and tracks the movement of STX tokens through the network.

### Features

- **Network Visualization**: Interactive graph showing relationships between addresses
- **Transaction Tracking**: Detailed transaction history with filtering and search
- **Balance Analytics**: Real-time balance tracking for all monitored addresses
- **Address Comments**: Tagged addresses for known protocols (Zest, Velar, etc.)

## Updating the Data

All data lives in `src/data/transfers.json`, generated by `scripts/fetch-transfers.ts`:

```sh
SECONDLAYER_API_KEY=sk-sl_... npm run data:update
```

(or put `SECONDLAYER_API_KEY=...` in `.env.local`). The GitHub Action `.github/workflows/update-data.yml` runs this daily and commits changes; it needs the `SECONDLAYER_API_KEY` repository secret (`HIRO_API_KEY` is optional).

- **Tracked addresses**: `scripts/tracking.config.json` lists the seeds. Untracked standard principals that receive at least `follow.minStx` from a tracked address are tracked too, up to `follow.maxDepth` hops. Addresses with more than `follow.maxEventsPerAddress` transfers (exchanges) are skipped; add unwanted ones to `ignore`.
- **Events**: `stx_transfer`, `stx_mint` and `stx_burn` events from the Secondlayer Index API, one entry per event (`txId:eventIndex`). Mints and burns are summed per UTC day. Runs are incremental and re-fetch the last 100 blocks to absorb reorgs.
- **Balances**: the on-chain balance of every tracked address at the same block height, from the Hiro API. The app derives each address's opening balance from it, so reconstructed balances end exactly at the chain balance; fees and pre-endowment history are part of the opening balance.
